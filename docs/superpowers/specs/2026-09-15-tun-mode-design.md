# TUN 全局模式设计

日期：2026-09-15　状态：待实现

前置：`2026-08-30-net-client-design.md`（本机上网客户端）把 TUN 列为「明确不做，P2 Reserve，独立一期」。
本文就是那一期。

---

## 1. 目标

「开启网络」之后，**随时**可以开/关 TUN 全局模式：

| 操作 | 结果 | 弹 UAC |
|---|---|---|
| 打开应用 | 拉起提权服务 | 否 |
| 开启网络 | 系统代理模式（现状不变，不吃系统代理的程序仍直连） | 否 |
| 点「TUN 模式」 | 流量全局接管，SSH / 游戏 / 其它不吃系统代理的程序也走规则 | 否 |
| 再点一次 | 关掉，回到系统代理模式 | 否 |
| 关闭网络 / 关应用 | 服务连 mihomo 一起清掉 | 否 |
| 装服务（设置页，一次性） | 注册服务 + 设为手动启动 + 授予当前用户启停 | **一次，仅此一次** |

**非目标**：开机自启（服务跟应用生命周期走）、分流出站自定义、规则可视化编辑器、多引擎。

用户侧全程不碰命令行 —— Phase 0 的手工脚本是开发期验证物，不是交付形态。

---

## 2. Phase 0 实测结论

2026-09-15 在本机（Windows 11）跑完四项实验。**它们改变了下文设计，先列结论。**

| 实验 | 结论 |
|---|---|
| **0a** 驱动与网卡 | wintun 驱动**内嵌在 mihomo.exe 里**，启动时自装。实测 `pnputil` 出现 `oem79.inf`（原始名 `wintun.inf`，WireGuard LLC 0.14.0.0）—— 跑之前不存在。**杀软未拦**。TUN 网卡建成，`auto-route: false` 时路由表前后中三次快照完全一致 |
| **0b** 热重载 | `PUT /configs` 改 `tun.enable` 可**瞬时**建/销网卡，HTTP 2xx，无需重启 mihomo。日志 `[TUN] Tun adapter listening at` 出现两次，证明是真实销毁重建而非空操作 |
| **0c** 接管与崩溃 | `auto-route: true` 只**新增**一条默认路由指向 TUN（原路由保留，两条 metric 均为 0），不删原路由。**强杀（TerminateProcess）后：网卡自动消失、路由自动还原、网络立即恢复，零残留** |
| **0d** 捕获实证 | 同一套 `MATCH,REJECT` 规则下只翻转 TUN 开关，连通性随之在 不通/通/不通 之间翻转三次 —— 流量确实被 TUN 抓走 |

### 2.1 这推翻了什么

原设计把「网卡恢复逻辑」列为 TUN 最麻烦的部分、要独立一期的核心理由之一。**实测不成立**：

- WinTun 网卡是**进程退出即销毁**的临时网卡（TerminateProcess 也照样清）
- 路由绑定在网卡上，网卡消失时由 Windows 自动清除

**所以不需要自己写网卡/路由恢复逻辑。** 服务不必当看护进程去清理残留。

**仍未覆盖的场景**：系统崩溃 / 断电时 TUN 处于活动状态。但临时网卡与易失路由在重启后本就不复存在，故同样无需处理。

### 2.2 仍未验证的

- **节点分流正确性**：0d 只证明了「流量被抓」，用的是 `MATCH,REJECT`/`MATCH,DIRECT`，没有真实节点。真节点下的地理分流（`GEOIP,CN,DIRECT`）需要在实现阶段用真实配置复验。
- **DNS**：`client_yaml` 刻意不配 `dns` 块（见 `config/mod.rs:160` 注释：配了会触发启动期联网下载 country.mmdb，卡启动 5s+）。TUN 模式下 DNS 是否需要在 mihomo 内解析、要不要开 `dns-hijack`，实现阶段实测决定。
- **与系统代理共存**：TUN 开启时是否保留系统代理设置，实现阶段实测决定（倾向保留，作为 TUN 失效时的兜底）。

## 3. 架构

三个进程：

```
主程序（普通权限） ──命名管道 IPC──> yunyi-service.exe（SYSTEM，按需启动）
                                            │
                                            └──spawn / kill──> mihomo.exe（继承管理员）
```

| 进程 | 权限 | 职责 |
|---|---|---|
| 主程序（现有） | 普通 | UI、SSH、部署、订阅、测速 —— 全部不变 |
| **yunyi-service.exe**（新增） | SYSTEM | 唯一被授权 spawn/kill mihomo |
| mihomo | 由服务 spawn，继承管理员 | TUN + 系统代理 |

**为什么必须有提权进程**：Windows 上创建 TUN 网卡要装内核驱动，必须管理员令牌。非提权的 mihomo 永远建不了 TUN，无论怎么改配置。这是系统硬约束，绕不过去 —— 服务方案换到的是「一次 UAC 换永久」，不是「零 UAC」。

## 4. 服务设计

### 4.1 IPC 命令白名单

命名管道 `\\.\pipe\yunyi-service`，JSON 载荷，带 token。服务**只认**这四条：

| 命令 | 参数 | 作用 |
|---|---|---|
| `StartNet` | `mixed_port`, `ctrl_port`, `tun` | 起 mihomo |
| `StopNet` | — | 杀 mihomo |
| `SetTun` | `enable` | 改配置 `tun.enable` + `PUT /configs` 热重载 |
| `Status` | — | 服务与 mihomo 存活状态 |

### 4.2 安全边界（这条路的固有代价）

一个「听非提权客户端的话去 spawn 进程」的 SYSTEM 服务，天然是本地提权面。三条硬约束：

1. **mihomo 路径绝不由客户端指定**。服务自己从固定安装目录解析（服务 exe 同目录）。若接受客户端传路径，任何本地进程都能让服务以 SYSTEM 执行任意程序。
2. **校验调用方身份**。命名管道用 `GetNamedPipeClientProcessId` 取客户端 PID，校验其 exe 路径为已安装的主程序。这挡住「任意本地进程」这个威胁模型。
   **注意**：本应用目前**没有 Authenticode 代码签名**（`tauri.conf.json:39` 的 `pubkey` 是 updater 的 minisign 公钥，不是 Windows 代码签名证书）。所以校验只能是「路径 + 文件哈希」。要升级到签名校验，得先给主程序买证书签名 —— 那是另一件事，不在本期。
3. **配置写盘前强制覆写危险字段**：`log-file` 置空（这是最直接的 SYSTEM 任意文件写路径）、`geodata-dir` 钉死到固定目录、移除 `external-ui`。

**消除不掉的残余风险**：配置内容本质由用户数据驱动（节点来自订阅，且手工节点可带 `clash_raw` 片段直插配置，见 `config/mod.rs:193` 的 `node_mapping`），而 mihomo 以 SYSTEM 运行。白名单式字段校验对「mihomo 未来新增字段」是脆弱的。**这是选服务方案换来的代价，已知且接受**，但要写在这，别当成已经解决。

### 4.3 生命周期

- **装**：设置页「安装网络服务」→ 主程序用 `ShellExecute` 带 `runas` 拉起提权助手 → UAC → 助手注册服务、设为**手动启动**（`start=demand`，**不开机自启**）、把服务 DACL 改成允许当前用户启停 → 退出
  - DACL 那一步是「永不弹 UAC」的来源：之后 `sc start` 不需要管理员
- **应用启动** → `sc start yunyi-service`（无 UAC）
- **应用退出** → `sc stop` → 服务先杀 mihomo 再退
- **不注册任何开机自启项**

### 4.4 未安装服务时的降级

服务没装 / 被卸载 / 启动失败 → 「TUN 模式」开关**禁用并说明原因**，附一个「安装服务」入口。系统代理模式照常可用，不受影响。

## 5. TUN 开关

mihomo 起来后常驻提权，开/关 TUN = `PUT /configs` 热重载换 `tun.enable`：

- **瞬时、不断线**（0b + 0d 实测）
- 复用现成机制：`speed/engine.rs:63` 的 `reload()`，报文形态 `PUT {controller}/configs`，Bearer token，body `{path, payload, force: true}`

配置生成：`config/mod.rs` 的 `client_yaml` 增一个 `tun` 参数，启用时插入：

```yaml
tun:
  enable: true
  stack: mixed
  device: yunyi-tun0
  auto-route: true
  auto-detect-interface: true
```

`client_yaml` 是纯函数，这条改动可以直接照现有测试模式写单测。

## 6. 错误处理

| 情况 | 处理 |
|---|---|
| 服务未安装 / 启不来 | TUN 开关禁用 + 原因说明 + 安装入口（见 4.4） |
| TUN 启用失败（驱动装不上等） | 热重载返回非 2xx → 开关回弹，横幅展示 mihomo 的错误 |
| mihomo 崩溃 | 0c 已证零残留，网络自动恢复；主程序 `status` 轮询发现后清槽（现有逻辑 `net/runtime.rs:282`） |
| 关闭网络 | `StopNet` → 服务杀 mihomo；网卡与路由由 OS 回收（0c） |

**不再需要**：网卡恢复、路由表修复、看护进程 —— 见 2.1。

保留一道**廉价的**兜底：主程序启动时检查是否存在名为 `yunyi-tun0` 的残留网卡，有则删掉。0c 说正常情况下不会有，但这条成本极低，且能覆盖 2.1 未覆盖的场景。

## 7. 测试策略

| 层 | 方式 |
|---|---|
| 配置生成 | 纯函数单测（照 `client_yaml` 现有测试模式）：`tun` 参数开/关两条路径的 YAML 断言 |
| 危险字段覆写 | 纯函数单测：喂带 `log-file` / `external-ui` 的输入，断言输出里被清掉 |
| IPC 协议 | 进程内假服务端单测：命令编解码、token 校验、未知命令拒绝 |
| 真实 TUN 行为 | **手工验证清单**（SCM 与 UAC 无法在单测里跑）。Phase 0 那四个脚本可直接改造成回归清单 |
| 分流正确性 | 真节点配置下实测（见 2.2） |

Phase 0 的四个脚本（0a–0d）留在仓库外的临时目录即可；实现阶段把 0d 那个「同规则翻 TUN」的对照法改造成可重复的验证脚本。

## 9. 明确不做

- 开机自启（服务跟应用生命周期走）
- 分流出站自定义、规则可视化编辑器
- 多引擎（sing-box 本地客户端）
- 网卡 / 路由恢复逻辑、看护进程 —— **0c 证明 OS 自己会做，不需要**（见 2.1）。仅保留 §6 那一道成本极低的启动期残留网卡检查。

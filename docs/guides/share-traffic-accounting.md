# 分享流量与 VPS 账单口径

## 当前配额单位（2026-10-27 修正）

分享使用十进制流量单位：1 KB = 1,000 字节，1 MB = 1,000,000 字节，1 GB = 1,000,000,000 字节。因此，输入 100 GB 后实际配额是 100,000,000,000 字节。

创建、编辑回显、页面已用量和配额显示使用同一单位。以前把二进制 GiB 标成 GB 的行为已修复，原先按 100 × 1024³ 保存的两条现有分享也已修正为每方向 100 × 1000³。历史已用字节未清零、未缩放；因此同一笔用量从原来的约 5.8“GB”改为约 6.2 GB，是显示单位变化。

上下行方向配额已取消（2026-10-29）：新建/编辑只填 **公网双向总额度**，上下行仅保留用量明细，不再单独判停。总额度达到上限即停止公网转发。显示的一位小数仅用于阅读，实际判断使用整数原始字节，100 GB = 100,000,000,000 字节。

## 总额度与历史迁移

用户核对两条分享后确认，旧记录按 `(原上行字节 + 原下行字节) × 2` 计入总额。这是一次性的**历史折算**，保留原上、下行记录及折算基数，不把它标成过去的公网实测数据。

`总已用 = 历史折算字节 + 启用后公网入站 IP 字节 + 启用后公网出站 IP 字节`

启用后按每条分享独立的 Linux cgroup IP 钩子累计：订阅 HTTP 服务、分享网关、独立代理实例放进同一 systemd slice，统计配置的公网接口，排除 loopback。公网两段转发均计量，新增流量不再乘二；订阅 HTTPS 的公网流量也属于该分享。SSH、其他分享及主代理进程不进入该分享总额。

- 达到总额度，在内核过滤器拦截公网流量，不依赖管理页面刷新。
- 入站已经到达，即使因超额拒绝交付仍计入；被额度拒绝、未发出的出站包不计入。因此入站攻击或在途数据可能使已用超过上限，不能把实际计数截成恰好 100 GB。
- TCP/UDP 网关上下行仍是原方向明细，不应再相加作为新总额。
- 订阅响应带 `subscription-userinfo` 头，Clash/mihomo 系客户端会在订阅信息里显示已用与剩余：`upload=公网入站; download=公网出站+历史折算; total=总额度; expire=到期时间`。历史无法拆分方向，按既有迁移规则并入下载。客户端只在拉取/更新订阅时刷新，不是实时余额。
- 总额度 0（不限）的分享发 `total=0`，支持无限语义的客户端显示「已用 / ∞」。FlClash 在 `total == 0` 时整块隐藏订阅信息，因此这类分享还会把 `已用 X / ∞` 写进订阅内容里的 `自动选择` 组名（组定义、`proxies` 成员与 `MATCH` 规则同步替换，不会悬空引用；YAML 与 sing-box JSON 都处理）。限额分享不加后缀，组名保持稳定。组名与响应头里的用量都是拉取订阅那一刻的账面值。
- 编辑额度、限速、节点或重启服务不清零；移除重置用量入口，后端也拒绝重置。只有删除该分享才删除对应账本。
- `quota_total_bytes` 缺失表示旧分享尚未启用；值 `0` 表示仍统计但不限制总额。普通编辑旧分享时，不因字段缺失自动覆盖已有设置。

根权限计量服务每约 0.5 秒同步持久账本，内核计数跨服务重启保留。正常停止会冻结并保存最终计数，正常关机重启后恢复。若断电等异常导致内核计数消失且最后尾数无法确认，会停止分享并显示统计异常，绝不以零或猜测值继续。尚未实现向供应商查询异常断电期间尾数的自动补账。

账本在 `/var/lib/vpnshare-meters/<分享ID>.json`，独立于可回滚的分享配置目录；状态快照是 `/srv/vpnshare/<分享ID>/meter-status.json`。不要手工删除账本、BPF pin 或用旧程序覆盖清单，否则会触发统计保护。

统计精度的边界是 **Linux cgroup IP 钩子观察到的字节数**，包括该位置可见的 IP/传输开销。不能保证它与供应商宿主机、二层计量、网卡卸载、早期丢包或其他进程费用逐字节相同。用户此次两条线路的历史合计能对上供应商面板，支持所选折算基数，但不等于所有未来流量一定完全相同。

## 服务重启

通常只重启某条分享网关即可，内核总计数不变：

```sh
systemctl restart vpnshare-50288424d7bf4470-gateway
```

需要完整重启该分享时，先重启计量，再启动依赖它的服务（计量停止会连带停止分享，防止漏计）：

```sh
systemctl restart vpnshare-50288424d7bf4470-meter
systemctl start vpnshare-50288424d7bf4470 vpnshare-50288424d7bf4470-gateway vpnshare-50288424d7bf4470-xray vpnshare-50288424d7bf4470-singbox
```

另一条旧链接的 ID 是 `5e715f47b19c4af8`，替换上述 ID 即可。

## 项目如何统计上、下行

方向以分享使用者为参照：

| 项目字段 | 网关读取的数据 | 常见内容 |
| --- | --- | --- |
| 上行 | 客户端连接 → 分享网关 → 代理实例 | 上传、请求、客户端协议控制数据 |
| 下行 | 代理实例 → 分享网关 → 客户端连接 | 下载、响应、服务端协议控制数据 |

同一分享所有使用者、所有节点协议的流量累计到同一份计数；不同分享分别计数。统计对象是到达网关的协议载荷，因此包含相应的 TLS/QUIC/代理协议开销。它不是单纯的文件大小，也不是整台 VPS 的网卡总字节数。

按用户确认保留现有规则：到达网关后被限速丢弃的 UDP 数据仍占用分享配额，因为这些数据可能已经造成 VPS 的入站流量成本。UDP/QUIC 重传到达网关会再次被读取；TCP 的内核级重传、IP/TCP 头和网关之前的内核丢弃不由这里完整计量。

网关每约 5 秒保存计数，管理页面每轮查询完成后约等 120 秒再查询；显示不是实时的。服务器直接使用内存中的当前字节计数执行配额，不等待页面刷新。

## 市面上的“双向流量计费”

这是计费口径，不是统一的协议。常见 VPS 双向流量套餐把公网入站（RX）和公网出站（TX）的账期累计值相加：

`计费流量 = 入站字节 + 出站字节`

供应商一般在宿主机虚拟网络接口或网络边界计量，再汇总账期字节差值。具体统计层、免费内网、攻击流量处理、GB/GiB 换算、计费周期均以供应商规则为准。

- [V.PS 官方 FAQ](https://v.ps/faq/)明确说明入站、出站都计入流量。
- [Vultr 官方流量计算说明](https://docs.vultr.com/support/platform/billing/how-is-bandwidth-usage-calculated)明确只计出站，入站不计入限额。
- [DigitalOcean 官方带宽计费](https://docs.digitalocean.com/platform/billing/bandwidth/)同样区分出站收费与免费入站，并按 GiB 描述部分计价。因此不能声称所有厂商都用相同的单位或规则。

## 代理场景为什么不能直接对账

例如，使用者经 VPS 下载约 1 GB 文件，忽略开销和少量请求：

```mermaid
flowchart LR
  Site[目标网站] -->|约 1 GB：VPS 入站| VPS[代理 VPS]
  VPS -->|约 1 GB：VPS 出站，同时属于项目下行| Client[分享使用者]
```

- 项目下行增加约 1 GB。
- 若供应商按 RX + TX 收费，则这次转发可能消耗约 2 GB 账单流量。
- 若供应商只计 TX，则可能消耗约 1 GB。

上传经代理转发也有对应的两段链路。因此，网关的上行/下行只是使用者方向的用量明细，不再单独限额；停用只看公网双向总额度，也不能保证等于商家账单额度。协议开销、重传、其他服务、内网流量豁免和具体套餐规则还会进一步造成差异。

网卡统计本身也区分接收、发送及不同阶段的丢弃，详见 [Linux 内核接口统计文档](https://docs.kernel.org/networking/statistics.html)。本次新增独立 IP 统计点，但供应商账单对账仍需使用供应商定义的统计层和计量规则。

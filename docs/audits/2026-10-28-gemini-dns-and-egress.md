# Gemini DNS 与出口对照诊断

## 已验证的结论

新服务器和旧服务器的主 Xray 出站配置相同：`freedom` + `UseIPv4`，均无额外路由规则。
sing-box 均使用系统解析器和 `ipv4_only`。新机系统解析器为 Google Public DNS，
服务器抓包显示查询由新机公网 IPv4 发往该解析器的 UDP 53；该段 DNS 未加密。

客户端存在独立的 DNS 外泄问题：原配置先向国内 DoH 发送 Gemini 页面与对话接口
域名，再通过代理查询国外 DNS。fallback 最终采用正确答案，不代表前面的查询没有泄漏。

## 本次修正

`src-tauri/src/config/mod.rs` 的运行客户端配置生成器添加专用 `nameserver-policy`，
让 Google 登录、Gemini 页面、clients6 对话 API 和资源域名经所选节点查询国外 DoH。
同一域名集合的代理规则排在国内直连规则之前；节点域名使用独立 bootstrap 解析器，
避免解析节点依赖节点自身。无节点时不生成引用不存在代理组的 DNS 策略。

当前运行客户端已加载相同策略，仍选择新服务器的 VMess 节点。修改前后使用独立
mihomo 进程复测，修复后两个 Gemini 域名只向经代理连接的国外 DoH 发出查询。
这项修正限定在上述域名，不代表所有应用、系统 DNS 或其他域名均已无泄漏。
系统代理模式也不能接管所有绕过代理的应用 DNS。

源码变更尚未安装为新的桌面程序；旧程序再次生成配置可能覆盖本次运行时修正。

## Gemini 可用性验证

同一 Chrome 版本、全新无登录会话、相同 `Reply only with OK.` 提示：

| 路径 | 结果 |
| --- | --- |
| 新机直接出口 | 对话响应内部返回 400 `FAILED_PRECONDITION` |
| 旧机出口 | Gemini 返回 `OK` |
| 新机入口，临时仅将 Google 域名转到旧机出口 | Gemini 返回 `OK`，普通站点仍显示新机出口 |
| 修正客户端 DNS 后，保留新机直接出口 | 仍返回 400 `FAILED_PRECONDITION` |
| 两机固定相同页面、对话接口和静态资源 IP，新机直出 | 仍返回 400 `FAILED_PRECONDITION` |
| 两机固定相同页面、对话接口和静态资源 IP，旧机直出 | Gemini 返回 `OK` |

固定目标测试使用两台服务器上相同的临时 Xray HTTP 入站和 IPv4 freedom 出站，
通过 SSH 转发连接，Chrome 使用同版本、同语言、全新无登录会话和相同提示。
这进一步排除了客户端节点协议、额外分流规则及目标 DNS 选址差异。实测定位到
公网出口 IP 或出口路径相关的处理差异，不能直接断言 Google 内部具体命中了哪条规则。
两台服务器上的临时服务和配置均已清理。

HTTP 200 首页、第三方 IP 库的美国标记及页面的美国地区字段均不能证明对话可用。
结果指向 Google 对新出口路径的访问资格限制；仅凭该错误码不能确定地区误判、
IP 信誉或其他 Google 内部限制的具体类别。不能将 DNS 外泄认定为已证实的拒绝原因。

临时转出服务及其远端配置已清理；正式服务器没有切换出口。后续需要确定是否接受
独立的 Gemini 出口依赖，再实施长期恢复方案。部署验收应区分代理服务运行、目标
网页可达与真实对话成功，不能把前两者标为 Gemini 已解锁。

# TUN 下服务器端响应检测修复

## 最终口径

按用户确认，服务器页只做一次端响应检测。界面显示“端响应”，含义是从本机开始拨号，到收到服务器有效 SSH 标识行的总耗时，包含建连、当前路径和服务器首响应开销。它不是单程延迟、纯 RTT 或 ICMP ping；节点内的延迟测试及分跳口径保持原样。

## 原因与修改

原服务器测速使用 `TcpStream::connect` 返回时间。TUN 可在远端就绪前完成本地 TCP 握手，因此外网服务器也会被记为 0–1ms。

- 服务器测速改为单次拨号、发送 SSH 标识、等待远端有效标识后结束计时；不认证、不执行远端命令。
- 整个探测受 5 秒超时约束，响应总量最多 8KiB，兼容标识前说明行及分片响应。
- 超时、提前关闭、错误或截断标识均失败，失败不回退到本地 TCP 耗时，也不伪造 0ms。
- 延迟失败仍允许原有带宽检测独立完成。现有带宽算法及节点测速未因本修复改变。
- 界面改名并解释口径。旧数据库字段 `latency` 保留兼容；旧记录需要重新测速，未直接改写生产测量数据。

## 验证

最终单次生产测量函数在本机 TUN 开启时的实测：

| 目标 | 旧 TCP 计时 | 单次 SSH 端响应 |
| --- | ---: | ---: |
| 203.0.113.11:22 | 0ms | 517ms |
| 203.0.113.12:57816 | 0ms | 451ms |

这些是当时路径下的端响应总耗时，不能与关闭 TUN 时的 TCP RTT 直接比较，也不能据此认定线路延迟翻倍。检测没有关闭 TUN或改变路由。

- 服务器测速域：54 项通过，1 项联网实测默认忽略后单独显式运行并通过。
- 新增编排回归验证恰好一次探测、等待远端延时、数据正确写库及带宽不受影响。
- 协议边界回归覆盖无响应超时、分片/说明行、关闭、错误版本、空标识、截断和超长响应。
- 服务器页：57 项前端测试通过。
- 产品及测试 TypeScript 检查、Vite 构建通过。
- Windows 测试替身先读完客户端标识再关闭连接，避免未读数据导致 RST 干扰响应测试。

旧版本备份：`D:\新建文件夹\vpn控制\src-tauri\target\debug\vpn-ctl.exe.before-tun-endpoint-20261028`。

协议格式依据：[RFC 4253 §4.2](https://www.rfc-editor.org/rfc/rfc4253#section-4.2)。

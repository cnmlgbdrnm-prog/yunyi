## 限速结论与测量边界

旧分享（订阅端口 18080）上下行配置均为 0，含义是不限速。新分享（18081）上下行均为 300 Mbps。分享清单与网关配置一致；公网数据端口由网关进程监听，代理实例只监听回环内部端口。

### 真实运行中的分享链路

通过临时 sing-box 客户端，使用现有分享凭据，经过真实公网网关端口、分享代理实例，访问同机临时测试源。每方向传输 160 MiB，舍弃前 64 MiB，测量后约 96 MiB 的稳定阶段。测试源仅接受服务器自身来源并验证随机测试令牌；全部临时进程、端口及配置在测试后清理。

## 发现及修复优先级

### P1：分享网关发生过两次内存耗尽，缺少资源上限保护

服务器内核及 systemd 日志确认：北京时间 2026-10-27 00:12:37、00:38:12，新分享的网关 Python 进程被 OOM killer 杀掉，匿名驻留内存分别为 1,564,820 KiB、1,588,636 KiB，随后自动重启。服务器总内存约 2 GiB，无 swap。当前网关 `MemoryMax=infinity`。

代码风险位于 `src-tauri/src/share/scripts/share_gateway.py`：`handle_tcp` 没有总连接数上限；`UdpPublic.peers` 没有会话数上限；每个接收数据报均可创建独立 `_send` task，缺少待处理队列上限。故障本身已经发生，但历史日志不足以证明当时具体是哪一种流量或队列触发，不应声称已经定位唯一内存增长原因。

建议先添加连接/会话/排队字节的有界控制与观测，再设置合理的服务内存保护。不能仅靠不断重启掩盖问题。

### 计费口径澄清：UDP 限速丢弃的数据仍计入配额（已确认保留）

`UdpUpstream.datagram_received`（约 224–229 行）和 `UdpPublic.datagram_received`（约 257–262 行）都先调用 `charge()`，再调用 `try_take()`；额度不足丢包时，已用流量不会回退。

隔离复现：耗尽下行令牌桶后注入 60,000 字节数据报，实际转发 0 字节，但 `used_down_bytes` 增加 60,000。此前按旧设计的“实际转发字节”将其直接判为错扣不够准确。用户指出 VPS 可能仍计费后，已明确保留现有扣额规则，不将丢包字节自动退回。

上行到达网关之前，客户端到 VPS 的入站已经发生；下行到达网关之前，目标站到 VPS 代理实例的入站也可能已经发生。网关丢弃数据并不意味着这些网络传输没有成本。反过来，若商家只按出站计费，尚未发送到客户的下行包又可能不在该出站计费口径内，不能一概而论。

当前应用统计的是网关读到的协议载荷，包含经过网关的协议加密开销及 UDP 重传；它不是网卡层完整字节数，也不包括所有 TCP/IP 头、TCP 重传、内核层丢弃、代理另一段链路或主机其他服务流量。具体商家规则未核验，因此不宣称与 VPS 账单逐字节一致。[Linux 内核接口统计文档](https://docs.kernel.org/networking/statistics.html)也明确区分收到、发出及各阶段丢弃的统计。

同类边界问题：`charge()` 在 `used + n >= quota` 时将计数设置为配额并拒绝整个数据块。配额 1024、发送首块 1024 字节的复现结果为接受 0、计费 1024。TCP 一个读取块最大 64 KiB，可能在边界少交付这一块的数据。

本轮保持以上边界扣额行为，仅添加按进程统计的限速丢弃、资源保护丢弃计数用于诊断，不重复累加进配额。若要与商家账单对账，需要取得商家计费规则并另外设计网卡/代理进出链路统计。

### P2：编辑配额或限速会用旧快照覆盖较新的用量

`src-tauri/src/share/install.rs:1460` 在网关仍运行时读取 `usage`；1491 行才停止网关；1563 行附近将之前读取的 `usage` 写回。网关在停止时会 flush 最新计数，但随后被旧快照覆盖。包含节点集合的更新路径也传入这份事先读取的用量。

按现有操作顺序的隔离复现：读取 1000 字节旧快照 → 新流量与停机 flush 将用量更新到 3000 → 编辑写回后变回 1000。此复现是对代码操作顺序的模型验证，没有通过实际编辑线上分享来制造用量回退。

建议成功停止网关后重新读取最终用量，在最终状态基础上修改 blocked 等字段，保持计数单调不减。

### P2：TCP 半关闭导致响应丢失

`Gateway.pipe` 的 finally 无条件 `writer.close()`（约 186–190 行）。客户端只结束发送方向、保留接收方向时，上行转发结束会关闭整个上游连接，另一方向还未完成的响应丢失。

真实本地 TCP 套接字复现：客户端发送 REQUEST 后执行写方向 EOF；测试源收到 REQUEST 并回复 RESPONSE；通过网关的客户端收到空字节串。建议对允许半关闭的 TCP 连接分别传播 EOF，并在两个方向结束后再关闭完整连接。

### P2：Hysteria2 客户端带宽值与分享限速独立，存在隐藏的 100 Mbps 瓶颈

新分享网关为 300 / 300 Mbps，但其 sing-box 订阅的 Hysteria2 outbound 实际为 `up_mbps=100`、`down_mbps=100`。实测约 98 Mbps；仅提高临时客户端参数即可超过 100 Mbps，证明该配置确实限制了原客户端。

`src-tauri/src/share/clone.rs:80` 附近沿用原节点参数；`src-tauri/src/config/singbox.rs:290` 附近导出 `up_mbps` / `down_mbps`，缺省值为 100（文件 36 行）。分享网关限速变化不会自动同步这些客户端参数。这里确认的是 sing-box 订阅，不将其无条件推广到所有客户端格式。

建议分享界面区分网关上限与协议客户端带宽提示，生成订阅时采用一致、明确的策略，避免显示 300、实际客户端固定 100 的误导。

## 后续修复完成记录

用户授权修复资源风险、编辑用量回退、TCP 半关闭，并追加要求修复 Hysteria2 带宽参数不一致。

- 网关默认最多 256 个 TCP 连接、256 个 UDP 会话（跨监听端口合计）；UDP 待处理数据最多 1024 包/4 MiB；每个 UDP 发送缓冲最多 128 KiB。UDP 改为每个监听端口一个有界队列工作任务，避免每包创建任务。增加连接/会话回收与诊断计数。
- TCP 连接建立超时 10 秒，空闲超时 300 秒；任一方向有流量都会更新共享活跃时间。EOF 只关闭对应写方向，两个转发方向结束后再释放完整连接。
- 新建网关单元及这两份现有网关的 drop-in 都设置 `MemoryHigh=256M`、`MemoryMax=384M`、`LimitNOFILE=2048`。这是防止单个网关拖垮整机的兜底，不等于已经证明历史 OOM 的唯一触发流量。
- 普通编辑、节点集合编辑均在停稳网关后读取最终用量。节点更新备份包含最终用量；失败回滚也保留新实例停机时的最新计数。缺失或损坏的用量文件会拒绝编辑，避免静默清零。
- Hysteria2 新建、节点编辑、纯限速编辑都同步清单参数、YAML 和 sing-box JSON。两个方向均有限速时写入对应 Mbps 值；任一方向不限速时省略客户端固定带宽，让客户端自适应，有限速方向仍由网关执行。[sing-box 的官方说明](https://sing-box.sagernet.org/configuration/outbound/hysteria2/#up_mbps-down_mbps)确认省略这些字段会使用 BBR。
- 丢包计费行为保持不变，Hysteria2 的凭据、端口、证书及分享令牌保持原值。

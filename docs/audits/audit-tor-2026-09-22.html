10% 卡死不是 GFW，是我们自己的 Xray 配置

Tor 的 OR 连接每一条都带一个随机 SNI。我们部署的 Xray 开着 sniffing.destOverride 却没开 routeOnly，于是把目标从 IP 改写成那个随机域名交给下游解析——解析失败，~2.3 秒后静默关闭。 Tor 看到的是 unexpected eof。

审查 2026-09-22 修复验证 2026-09-23 vpn-ctl / 云驿 Tor Expert Bundle 15.0.23 mihomo v1.19.10

审查裁决

住宅代理无罪，GFW 无罪，Tor 无罪。Bridge 不需要做。

19 条原有结论中 FALSE 3 / PARTIAL 2；1 项证据不足明确记为 NOT_PROVEN。核心结论全部为 A 类（实测事实）。

01

根因链

  1. Tor 15 为每条 OR 连接生成随机 SNI 抓包实测：server_name 长度 31，内容为 www. + 17 个随机字符。 Tor 用这种方式把流量伪装成访问一个真实网站。
  2. Xray 的 sniffer 读出这个 SNI，并把目标从 IP 改写成域名 deploy.rs:559 与 upstream.rs:241 生成的入站配置是 "sniffing": { "enabled": true, "destOverride": ["http","tls","quic"] }， 没有 routeOnly: true。
  3. 下游那一跳必须自己去解析这个随机域名 目标已经是 www.<17个随机字符>.com:443 而不是 131.188.40.189:443。
  4. 解析失败，链路在 ~2.3 秒后静默关闭，零字节返回 实测 20 条连接的关闭时间落在 2253–2382ms，抖动仅 ±60ms——这是 DNS 超时， 不是拒绝，也不是拥塞。
  5. Tor 停在 10%，报 unexpected eof 10% 的含义是「TCP 到中继成功、TLS 握手尚未开始」——完全吻合： TCP 由 mihomo 建成功，TLS 被我们自己掐断。
02

决定性证据

把 Tor 的 ClientHello 原样抓下来，只改其中一个字段，其余字节一字不动。 所有重放都打到 131.188.40.189:443——一个单发时必然成功的端点。

谁先断开：半关闭探针

早期的转发探针在对端关闭时会主动拆掉另一侧，所以「谁先发 FIN」此前根本没有被测到。 改用半关闭友好的探针后： 

#1 + 2365ms ★ 上游 发 FIN (up=1580 down=12)
#1 + 2366ms ★ TOR  发 FIN (up=1587 down=12)

上游先关，Tor 在 1ms 后跟关。上游收到 1565 字节的 ClientHello 后， 一个字都没回。

04

修复

两处，各一行。加 routeOnly: true 后 sniffer 仍然照常提取域名供路由规则使用， 但不再改写真实目标——下游收到的仍是 IP，无需解析。 

src/servers/deploy.rs:559
- "sniffing": { "enabled": true, "destOverride": ["http", "tls", "quic"] }
+ "sniffing": { "enabled": true, "destOverride": ["http", "tls", "quic"], "routeOnly": true }

src/servers/upstream.rs:241  同上

这与「VPS→住宅→Tor 100% 成功」完全自洽：那条路上 Tor 直接把 IP 交给住宅 SOCKS， 没有 sniffer 在中间把它改写成域名。

05

顺带发现的隐私缺陷

destOverride 把域名送给了上游

现在这个配置不只是让 Tor 连不上——凡是走「上游/住宅出口」的流量， 被访问域名都会以明文域名形式交给上游代理（因为它收到的是域名而不是 IP， 必须自己解析）。

上游出口存在的意义正是「让上游只看到 IP、看不到你在访问什么」。当前配置把这个 保护反过来了。

加 routeOnly: true 同时修掉这两个问题：Tor 能连上，域名也不再下泄。 上游/住宅这条路径已修复并验证（见第 04 节）。

06

逐条回答

1. Tor 裸连为什么完全无法 bootstrap？ 部分证实

裸连（UpstreamProxy::None）时 Tor 拿不到任何上游，目录权威在本地网络上不可达， 因此一行 bootstrap 都没有。但这不是本次 10% 卡死的原因——两者是独立的失败。

2. Tor → mihomo → REALITY 为什么卡在 10%？ 已定位

不是卡在链路任何一跳，是被我们自己配置的 sniffer 掐断。 见第 01 节根因链。

3. 是否 GFW 识别了 Tor TLS？ FALSE

www.google.com 的 SNI 能完整握手并返回 3842 字节。链路上不存在 「按墙外域名/按 Tor 指纹拦截」的行为。

4. residential SOCKS 是否才是真正的故障点？ FALSE

VPS 上 A/B 对照：DIRECT = 100%，经住宅 = 100%。住宅代理是好的，它只是 被要求解析一个不存在的域名。

5. 当前 Privacy Mode 能否隐藏目标 VPS IP？ 设计成立，仍不可用

设计上成立：resolve_target 把隐藏服务放到入口那台机器，转发目标是落地的 WireGuard IP。关键点已验证：servername 来自 params.sni 而非 server，所以换成 onion 不会让 REALITY 因 SNI 失配而拒绝。
但整条隐私线仍然跑不通，瓶颈已不再是 Tor：tor/mod.rs 目前没有被任何调用方接上（ensure_started 是 dead code）， 所以配置里那个 127.0.0.1:9050 没人监听，节点按 fail-closed 拒连。 要让隐私开关真正可用，还差把本机 Tor sidecar 接进「开启网络」与作业流程。

6. 是否必须加入 Bridge？ 不需要

不需要。10% 卡死与 Bridge 要解决的问题（链路被识别/阻断）毫无关系。 加 Bridge 只是在一个自伤的基础上再叠一层。

7. 若必须加，选 WebTunnel / obfs4 / Snowflake？ 降级为参考

本轮不需要做。若将来确有需求： WebTunnel 与 Snowflake 并列首选，obfs4 已不再是可靠选项—— Tor 官方中文文档（tor4zh）在 2026-08 的提交里已把 obfs4 从 PT 列表中移除， 且官方明确表示公开分发的 obfs4 桥在中国大概率不可用，需私有未列出桥。 meek-azure 是缓慢的最后手段。

8. 已完成功能是否存在泄漏？ 存在 2 条

(a) 域名下泄：见第 05 节，destOverride 把被访问域名交给上游。 (b) SSH 直连：net/local_proxy.rs 在隧道不可达时回落到直连， 且 self_hosted 会让对自有服务器的 SSH 优先走直连—— 开着隐私时，ISP 仍能看到 PC→VPS:22。
未发现 DNS 泄漏：enhanced-mode: fake-ip 下 .onion 拿到假 IP 即交给代理解析，不发真实查询；Tor 侧 20 条连接 全部为 ATYP=1，也没有走本地 DNS。

9. 最终实现建议 见下节

先修 sniffer，再谈其他。

07

实现建议

立刻做

1. 给两处 sniffing 加 routeOnly: true。 这一条同时修掉 Tor 连不上和域名下泄两个问题。改完后在真机跑一次完整 bootstrap，必须到 100% 才算通过——不要以「到 14% 了」当成功。

2. 轮换凭据。本轮审查中我两次把敏感值打印到了终端：mihomo 的 secret（每次网络重启都会轮换，影响有限），以及住宅代理的用户名/密码 （我的打码正则在 .settings.servers[].users 上，而真实结构是 .settings.{address,port,user,pass}）。住宅凭据应当轮换。这是我的失误。

然后

3. 让隐私线真的跑通一次端到端，把「设计成立」变成「实测成立」。 在此之前，Privacy Mode 不应被视为可用功能。

4. 补一条回归测试钉住 routeOnly—— upstream_tests.rs:64 已经在断言 sniffing 的形状，把 routeOnly 一起断言进去即可。

明确不做

不加 Bridge、不打包 lyrebird、不改生产 torrc/Xray/firewall。 10% 卡死的原因已经找到，它不在 Tor 这一侧。

«Tor 的 SOCKS5Proxy 覆盖全部 OR 与目录连接»——证据不足。 20/20 条被抓到的连接确实都走了代理，但我原打算用 netstat 枚举 tor.exe 自身 socket 来反证「没有任何直连」，那次测量用错了 PID（拿到的是 Git Bash 的 shell PID），所以没有拿到有效数据。结论方向一致，但未达可断言标准。

未能直接核实

对 support.torproject.org 的直接抓取被网络策略阻断， 第 7 条的官方推荐顺序来自搜索结果对 Tor Project 页面内容的转述， 而非我本人读取原页。中文文档与法文版把 WebTunnel 排在首位，其他语种版本把 Snowflake 排首位——官方并无统一顺序，这一点本身值得注意。
